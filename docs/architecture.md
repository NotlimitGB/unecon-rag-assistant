# Архитектура

## Текущее состояние

Frontend и backend API сохраняют исходный поток:

```text
Frontend (React)
    ↓ HTTP
Backend API (FastAPI)
```

Frontend проверяет доступность backend через `GET /api/v1/health`. Отдельная ручная команда подготавливает утверждённые официальные источники:

```text
Утверждённый манифест официальных источников
        ↓
Контролируемая загрузка
    ├─ HTML → извлечение текста ─┐
    └─ PDF → постраничный текст ─┴→ нормализованные документы
                                     с происхождением
```

Загрузчик запрашивает только адреса из манифеста, не обходит ссылки и проверяет принадлежность каждого перехода домену `unecon.ru`. Исходный и конечный адреса сохраняются для ссылок на источник. Для PDF сохраняются отдельный текст каждой страницы и её номер. Обрабатываются только PDF с текстовым слоем; OCR не реализован. После загрузки локальная команда проверяет нормализованные JSON и строит детерминированные чанки.

Локальный этап чанкирования работает только с файлами:

```text
Нормализованные HTML/PDF JSON
        ↓ проверка схемы, метаданных, URL и хешей
paragraph-aware-v1 (до 1200 символов, перекрытие до 150)
        ↓
data/processed/chunks/<source-id>.json
```

Он не обращается к сети и не запускает загрузчик. Принимаются документы активных записей манифеста с исходным и конечным URL внутри `https://unecon.ru` или его поддоменов. Каждый PDF-чанк относится к одной странице; пустые страницы не создают чанков. HTML-чанки не имеют номера страницы. Артефакт результата содержит метаданные документа, SHA-256 текста, детерминированные ID, длину и хеш каждого фрагмента, а также фактическое перекрытие. Результаты находятся в игнорируемом Git каталоге `data/processed/`.

Загрузка и чанкирование — отдельные ручные этапы. Команда чанкирования не загружает отсутствующие документы. PDF с несоответствующими текстом, хешем, схемой или нумерацией страниц отклоняется; ранее записанный артефакт чанков при ошибке не заменяется.

Плотный поиск — третий ручной локальный этап:

```text
Все активные чанки → проверка целостности и происхождения
                  → BGE-M3: нормализованные эмбеддинги
                  → FAISS IndexFlatIP → top-K фрагментов с URL и страницей
```

Основной индекс хранится вместе с метаданными в `data/processed/index/`. Отдельный индекс строк таблиц трёх проверенных PDF хранится в `data/processed/table_index/` и собирается офлайн с повторной проверкой исходных PDF. При поиске сверяются SHA-256 файлов FAISS, модель, размерность, записи, текущий корпус и версии нормализованных PDF. Индексы строятся на CPU, модели могут работать на CPU или CUDA. Скалярное произведение нормализованных векторов используется как оценка косинусного сходства.

Отдельная команда оценивает плотный поиск на 80 вручную размеченных вопросах из `data/evaluation/retrieval_questions.json`. Перед загрузкой модели она проверяет схему датасета, источники и метки PDF-страниц. Одна сессия поиска повторно использует индекс и модель для всех вопросов. JSON и Markdown отчеты в `data/processed/evaluation/` содержат Primary, Accepted и Page Recall/MRR, разбивки и диагностические промахи. Качество поиска оценивается отдельно от качества будущей генерации; Task006 не меняет ранжирование.

Основной путь приложения: `вопрос → один BGE-M3 эмбеддинг → основной FAISS top-20 + табличный FAISS top-5 → объединение 25 → BGE reranker всех 25 → не более двух результатов с одной страницы PDF → top-5`. Ограничение страницы общее для чанков и строк; HTML не ограничен. Типизированный сервис выдаёт точный текст, конечный официальный URL, страницу и оба score; он не раскрывает внутренний ID вектора или представление. Dense доступен явно как независимый диагностический режим. При ошибке индекса таблиц или reranker автоматического перехода на dense нет. Запросы не загружают официальные PDF и не перестраивают индексы.

Решение о прежнем reranker описано в `docs/decisions/0001-adopt-reranked-retrieval.md`; принятие двух каналов и ограничения PDF-страницы — в `docs/decisions/0004-adopt-table-aware-diversity-retrieval.md`. Историческая команда `rerank-search` сохраняет поиск только по обычным чанкам.

Отдельный локальный CLI формирует ответ: один вызов `RetrievalService` → до пяти чанков с проверенным происхождением → один запрос Ollama `qwen3.5:9b` → структурированный ответ. Промпт `grounded-answer-v1` требует русского ответа только по контексту и трактует инструкции внутри чанков как данные. Каждый чанк получает ID `C1…Cn` в порядке выдачи. Модель возвращает только статус, текст и ID цитируемого контекста; сервис проверяет ID и строит публичные цитаты из метаданных чанков. При нехватке данных возвращается фиксированный отказ. Проверка цитат не доказывает верность утверждений ответа, поэтому качество генерации нужно оценивать отдельно. Обоснование — в `docs/decisions/0002-local-grounded-generation.md`.

Оценка генерации — отдельная ветвь после ответа, не меняющая рабочий поиск или промпт. Датасет содержит 42 вопроса из замороженного набора поиска и 18 вопросов, требующих отказа. Автоматическая оценка измеряет статус, структуру, цитируемый источник и страницу, время ответа; фактическую точность, опору на контекст, полноту и поддержку цитатами проверяет человек по сохранённому тексту чанков. Полученные отчёты остаются локальными. Поиск и генерация измеряются раздельно; метод описан в `docs/decisions/0003-generation-evaluation-method.md`.

```text
Официальные источники СПбГЭУ → контролируемая загрузка → нормализованные документы
    → детерминированные чанки → BGE-M3 → основной FAISS → dense top-20
    ↘ строки таблиц трёх PDF → отдельный FAISS → dense top-5
    → объединение 25 → BGE reranker → ограничение PDF-страницы → top-5
    → Ollama → ответ с цитатами
                                                              ↓
                                                  оценка генерации

Отдельно: плотный поиск → базовая оценка и диагностика; оба режима → сравнение Recall / MRR.
```

## Реализованный локальный поток и дальнейшее развитие

```text
Нормализованные официальные документы
        ↓
Детерминированные чанки с происхождением
        ↓
Поиск релевантных чанков (реализован)
        ↓
Контекст
        ↓
Ollama qwen3.5:9b (локальный CLI)
        ↓
Ответ и официальный источник
```

Ответ доступен через CLI и `POST /api/v1/answer`; frontend ответа пока не реализован. HTTP-маршрут синхронно вызывает `AnswerService.answer()` ровно один раз и использует существующий `AnswerResponse`. В lifespan создаётся один сервис, повторно используемый между запросами и закрываемый при остановке. Модели и индексы остаются ленивыми; startup и health не выполняют поиск или проверку Ollama.

```text
Web / будущие адаптеры → POST /api/v1/answer → AnswerService
    → канонический RetrievalService → генерация Ollama → проверенный AnswerResponse
```

Отказ из-за нехватки сведений — успешный HTTP 200; неверный запрос — 422; ожидаемый `GenerationError` — безопасный 503. Вход содержит только строгую строку `question` до 2000 символов. Истории чата нет. Telegram и MAX остаются будущими адаптерами к той же границе приложения. Подробности — в ADR 0005.

## Принципы

1. **Независимость от среды развёртывания.** Локальная разработка не привязывает приложение к конкретному компьютеру, абсолютным путям или GPU. Код должен допускать перенос на сервер университета или в облачную инфраструктуру без изменения бизнес-логики.
2. **Минимально необходимая сложность.** Добавлять архитектурные компоненты только вместе с реальной потребностью.
3. **Только официальные источники.** Будущая база знаний формируется из доверенных материалов университета.
4. **Сохранение происхождения источника.** Используемые фрагменты знаний должны содержать сведения о своём источнике.
5. **Заменяемая инфраструктура.** Заменять инфраструктурные компоненты там, где это оправдано, не меняя основную бизнес-логику.
6. **Без преждевременных микросервисов.** На текущем этапе это обычное приложение с frontend и backend.
7. **Раздельная оценка поиска и генерации.** Качество поиска контекста оценивается отдельно от качества ответа языковой модели.
8. **Независимость от оборудования разработчика.** Локальная разработка не требует конкретной видеокарты или локального размещения будущей модели.

Дальнейшая оптимизация поиска и пользовательский интерфейс ответа остаются будущими задачами. HTTP API ответа реализован; его укрепление и сквозная проверка предшествуют работе над интерфейсом.
