# UNEcon RAG Assistant

**Тема ВКР:** «Разработка справочного модуля с контекстным дополнением для абитуриентов».

Система помогает абитуриентам находить ответы в официальных материалах университета и показывает источники информации.

## Текущее состояние

Проект содержит frontend, backend API, ручную загрузку утверждённых HTML-страниц и PDF СПбГЭУ, детерминированное чанкирование, локальный поиск через BGE-M3, FAISS и reranker, а также локальную генерацию ответов через Ollama. PDF обрабатываются только при наличии текстового слоя. Ответы с источниками доступны в браузере, через CLI и HTTP API.

## Требования

- Python 3.12
- Node.js 24.x и npm 11.x
- GPU не требуется

Основные команды ниже приведены для Windows PowerShell.

## Настройка окружения

Из корня репозитория создайте локальный файл настроек:

```powershell
Copy-Item .env.example .env
```

Файл `.env.example` содержит development defaults для backend и адреса API frontend. Локальный `.env` не коммитится. Для другого адреса API измените `VITE_API_BASE_URL` в локальном `.env`.

## Backend

Из корня репозитория создайте и активируйте виртуальное окружение, затем установите зависимости:

```powershell
py -3.12 -m venv backend\.venv
.\backend\.venv\Scripts\Activate.ps1
Set-Location backend
python -m pip install --upgrade pip
python -m pip install -e ".[dev]"
```

Запустите сервер:

```powershell
python -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

API health-check: `http://localhost:8000/api/v1/health`.

### API ответа

Backend запускается командой выше:
`python -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000`.
`GET http://127.0.0.1:8000/api/v1/health` проверяет только работу HTTP-приложения.

Для ответов сначала подготовьте основной и табличный индексы по разделу «Поиск приложения» и запустите локальную Ollama с `qwen3.5:9b`. Пример PowerShell:

```powershell
$body = @{ question = "Какие документы нужны для поступления?" } | ConvertTo-Json
Invoke-RestMethod -Method Post -Uri "http://127.0.0.1:8000/api/v1/answer" -ContentType "application/json; charset=utf-8" -Body ([System.Text.Encoding]::UTF8.GetBytes($body))
```

Запрос содержит только строку `question` длиной до 2000 символов; пробелы по краям удаляются. Ответ использует существующие поля `query`, `status`, `answer`, `retrieval_mode`, `citations`. Цитаты сохраняют официальный URL, источник и страницу PDF (для HTML — `null`).

Основной режим использует принятый поиск по двум индексам с ограничением страницы PDF и локальную генерацию Ollama. Один сервис переиспользуется в течение жизни приложения; первая выдача может занять больше времени из-за загрузки моделей. Обычный поиск не запрашивает документы СПбГЭУ из сети.

Статусы `answered` и `insufficient_evidence` возвращают HTTP 200; второй содержит существующий фиксированный отказ и пустые цитаты. Некорректный запрос возвращает HTTP 422, а ожидаемая ошибка поиска или генерации — HTTP 503 с безопасным сообщением. Проверка цитат не гарантирует фактическую точность ответа. Потоковой передачи, истории и авторизации пока нет. Решение описано в [ADR 0005](docs/decisions/0005-application-answer-api.md).

Для backend-проверок откройте отдельное окно PowerShell из корня репозитория:

```powershell
.\backend\.venv\Scripts\Activate.ps1
Set-Location backend
python -m pytest -q
ruff check .
```

### Официальные источники HTML и PDF

Реестр использует строгую схему v2. `id` обозначает конкретную неизменяемую версию;
`logical_document_id` объединяет версии одного документа за `admission_year`.
В корпус входят только записи `status=active`; `draft` и `superseded` исключены.
Связь `supersedes` указывает на более раннюю версию того же документа и года.
На документ и год допускается не более одной активной версии. Даты
`published_at`, `effective_from`, `effective_to` могут быть `null`: они нужны для
аудита и не включают/выключают источник автоматически.

Из `backend/` доступны команды без изменения реестра:

```powershell
python -m app.ingestion.cli list
python -m app.ingestion.cli audit --as-of 2026-09-26
python -m app.ingestion.cli freshness
```

`list` и `audit` работают без сети. `freshness` проверяет активные источники на сайте
и записывает только `data/processed/freshness/report.json`, без текста документов.
Код 0 означает `unchanged` либо `presentation_changed` для HTML: изменились байты,
но сохранились извлечённый текст и конечный URL. `content_changed`, PDF `file_changed`,
`redirect_changed`, `missing_local_artifact` и `error` возвращают код 1.
При нескольких изменениях приоритет имеет `redirect_changed`; остальные различия
сохраняются в отчёте. Аудит никогда не обновляет корпус или индексы автоматически.

Файл `data/source_manifest.json` содержит утверждённый список официальных HTML-страниц и PDF для приёма 2026 года. Загрузчик проверяет весь манифест до сетевых запросов и получает только явно перечисленные адреса `unecon.ru`. Переходы на другие домены запрещены; ссылки внутри страниц не обходятся. PDF должны содержать извлекаемый текстовый слой. Сканированные PDF и OCR не поддерживаются.

Из каталога `backend/` после установки зависимостей загрузите одну страницу:

```powershell
python -m app.ingestion.cli fetch --source-id admissions-bachelor
```

Для обработки одного PDF:

```powershell
python -m app.ingestion.cli fetch --source-id admission-deadlines-pdf
```

Для обработки всех активных источников:

```powershell
python -m app.ingestion.cli fetch
```

Результаты сохраняются в `data/processed/html/<source-id>.json` и `data/processed/pdf/<source-id>.json`. PDF-документы содержат текст по страницам, номера страниц, SHA-256 исходного файла и нормализованного текста, а также исходный и конечный адреса. При явном `--output-dir` файлы выбранных источников записываются непосредственно в указанный каталог. Содержимое `data/processed/` намеренно не отслеживается Git. Команда печатает результат по каждому источнику и завершает работу с ненулевым кодом при ошибке.

Исходные снимки находятся в `data/processed/originals/html/<source-id>.html` и
`data/processed/originals/pdf/<source-id>.pdf`. HTML сохраняется как точная строка
загрузчика в UTF‑8, PDF — как точные исходные байты. `source.snapshot_sha256`
связывает нормализованный документ со снимком; для PDF он равен `document.file_sha256`.
Хеш нормализованного текста остаётся отдельным. Повторная загрузка идентичной пары
ничего не заменяет; любое изменение снимка требует отдельной версии источника.
Даже `presentation_changed` не разрешает перезапись прежнего снимка. При ошибке
извлечения или неполной локальной паре ранее сохранённые файлы не заменяются.

`--originals-root` меняет корень снимков, сохраняя подкаталоги `html/` и `pdf/`.
Для freshness `--input-root` указывает корень нормализованных документов,
а `--output-dir` — каталог отчёта. Все пути по умолчанию отсчитываются от проекта.

Нормализованные документы, чанки и метаданные обоих индексов используют схему v2;
production не принимает старые схемы. Изолированная миграция принятого v1-корпуса
готовит новый каталог, не заменяя рабочие файлы:

```powershell
python -m app.ingestion.migration --legacy-manifest ..\data\processed\task025\backup\source_manifest.json --input-root ..\data\processed\task025\backup --staging ..\data\processed\task025\candidate-new
```

До записи она сверяет все 12 источников с сайтом и прежние чанки. После подготовки
необходимы ручная сборка обоих индексов с путями кандидатного каталога и каноническая
оценка; сама команда не публикует корпус. Результаты принятой миграции — в
[Task025](docs/evaluation/0012-document-lifecycle-migration.md), решение — в
[ADR 0007](docs/decisions/0007-document-lifecycle-and-source-snapshots.md).

### Подготовка чанков

После загрузки источника запустите локальное чанкирование из `backend/`:

```powershell
python -m app.chunking.cli build --source-id admissions-bachelor
python -m app.chunking.cli build --source-id admission-rules-pdf
```

Без `--source-id` команда обработает все активные записи манифеста, для которых есть нормализованный JSON; отсутствие файла будет учтено как ошибка, остальные записи продолжат обрабатываться. Неактивные записи пропускаются. Этап читает только локальные файлы и не выполняет сетевые запросы или загрузку источников.

Параметры `--manifest`, `--input-root` и `--output-dir` позволяют задать собственные пути. По умолчанию используется `data/source_manifest.json`, входные документы из `data/processed/html/` и `data/processed/pdf/`, а результаты сохраняются в `data/processed/chunks/<source-id>.json`. Артефакт хранит алгоритм `paragraph-aware-v1`, метаданные и хеш документа, детерминированные ID чанков, хеш и длину каждого фрагмента, фактический размер перекрытия и происхождение по странице PDF. Максимальный размер чанка — 1200 символов, целевое перекрытие — до 150 символов. PDF обрабатывается постранично; пустые страницы остаются в исходном документе, но не создают чанк.

### Поиск приложения

Для сборки индекса нужны чанки **всех активных** источников. Из `backend/` выполните:

```powershell
python -m app.ingestion.cli fetch
python -m app.chunking.cli build
python -m app.retrieval.cli build-index
python -m app.retrieval.cli build-table-index
python -m app.retrieval.cli retrieve "Какие вступительные испытания нужно сдавать?"
```

Первая сборка загрузит модель `BAAI/bge-m3` из Hugging Face; для этого нужен доступ к сети и свободное место для кеша. GPU необязателен: `EMBEDDING_DEVICE=auto` использует CUDA при наличии, иначе CPU. В `.env` можно задать `EMBEDDING_MODEL`, `EMBEDDING_DEVICE` (`auto`, `cpu`, `cuda`) и `EMBEDDING_BATCH_SIZE` (1–128). CLI также принимает `--manifest`, `--chunks-dir`, `--index-dir`, `--device`, `--batch-size`; поиск ограничивает `--top-k` диапазоном 1–50.

Основной индекс сохраняется в `data/processed/index/`, а отдельный индекс строк таблиц — в `data/processed/table_index/`. `build-table-index` работает офлайн относительно источников: читает сохранённые PDF из `originals/pdf/`, проверяет снимки и нормализованные документы до загрузки модели и использует прежний extractor `lines_strict`. При необходимости путь задаётся через `--originals-root`. Источники выбираются в порядке реестра по `status=active`, `source_type=pdf`, `processing.table_aware=true`, без фиксированного года. Сейчас это `admission-capacity-pdf`, `entrance-exams-list-pdf` и `tuition-order-128-pdf`. Индекс таблиц сверяется с версиями и хешами нормализованных PDF и основного индекса; устаревший, отсутствующий или повреждённый артефакт вызывает явную ошибку. Первичная загрузка моделей при отсутствии кеша остаётся отдельной сетевой потребностью.

Основной режим получает top‑20 из обычного индекса и top‑5 из индекса таблиц, ранжирует все 25 прежней моделью `BAAI/bge-reranker-v2-m3` и выбирает до пяти результатов, допуская не более двух с одной страницы PDF. Он повторно использует индексы и модели между запросами одного экземпляра. Результат содержит исходный `dense_score` и итоговый `rerank_score`.

Основание принятия этой схемы — [ADR 0004](docs/decisions/0004-adopt-table-aware-diversity-retrieval.md); результаты миграции — в [отчёте Task021](docs/evaluation/0010-production-retrieval-adoption.md).

В `.env` доступны `RETRIEVAL_MODE=reranked` (`reranked` или `dense`) и `RETRIEVAL_TOP_K=5`. В основном режиме `top_k` допускает 1–5 и требует `RERANKER_CANDIDATE_K=20`; в явном `dense` — 1–20. При недоступности индекса таблиц или reranker основной режим завершается ошибкой без автоматического перехода на dense. Для отдельного вызова используйте `retrieve "вопрос" --mode dense` или `--mode reranked`; `--json` печатает прежний типизированный JSON-ответ. `source_url` в нём — конечный проверенный адрес официального источника; внутренний ID вектора не выводится.

### Диагностический плотный поиск

Команда `python -m app.retrieval.cli search "Какие сроки подачи документов в 2026 году?" --top-k 5` сохраняет исходную плотную выдачу BGE-M3 и FAISS для диагностики и оценки. Её score — скалярное произведение нормализованных векторов. Она не использует reranker.

### Оценка качества поиска

Отслеживаемый датасет `data/evaluation/retrieval_questions.json` содержит 80 вопросов по активным официальным источникам 2026 года. Для каждого задан один основной источник (`primary_source_id`) и список источников, действительно содержащих ответ (`acceptable_source_ids`); вторые используются только для дополнительных метрик. Для части PDF-вопросов указана проверенная страница.

После сборки актуального индекса выполните из `backend/`:

```powershell
python -m app.evaluation.cli retrieval
python -m app.evaluation.cli canonical-retrieval
```

Первая команда сохраняет историческую плотную оценку. Вторая оценивает текущий `RetrievalService` на тех же 80 вопросах и сравнивает каждый итоговый top‑5 с локальным отчётом Task018. Её JSON и Markdown сохраняются в игнорируемом `data/processed/evaluation/`; для воспроизведения миграции требуется локальный отчёт Task018. Ответы не генерируются.

### Сравнение с reranker Task007

Историческое сравнение Task007 и команда `rerank-search` используют только основные чанки и не являются текущим путём приложения. Из `backend/` выполните:

```powershell
python -m app.retrieval.cli rerank-search "Какие вступительные испытания нужно сдавать?" --top-k 5
python -m app.evaluation.cli compare-reranker
```

Первая команда reranker скачает модель при наличии сети. В `.env` доступны `RERANKER_MODEL`, `RERANKER_DEVICE` (`auto`, `cpu`, `cuda`), `RERANKER_BATCH_SIZE` (1–64), `RERANKER_MAX_LENGTH` (32–4096), `RERANKER_CANDIDATE_K` (5–100); значения по умолчанию — `BAAI/bge-reranker-v2-m3`, `auto`, 8, 512, 20. Сравнение использует ровно 20 кандидатов и неизменный датасет 80 вопросов. Отчёты `data/processed/evaluation/reranker_comparison.json` и `.md` сохраняют обе выдачи и изменения рангов. Архитектурное решение зафиксировано в `docs/decisions/0001-adopt-reranked-retrieval.md`.

### Локальный ответ с источниками

Установите [Ollama](https://ollama.com/) самостоятельно, запустите локальный сервис и загрузите модель `qwen3.5:9b` командой `ollama pull qwen3.5:9b`. После подготовки актуального индекса выполните из `backend/`:

```powershell
python -m app.generation.cli answer "Какие вступительные испытания нужно сдавать?"
python -m app.generation.cli answer "Какие вступительные испытания нужно сдавать?" --retrieval-mode dense --json
```

Команда один раз получает до пяти чанков от `RetrievalService`, один раз вызывает локальную Ollama и возвращает ответ по-русски. Модель получает точный текст чанков с временными ID `C1…Cn`; цитаты в результате собираются из проверенных метаданных поиска, а неизвестные или повторные ID отклоняются. При недостатке сведений выводится фиксированный отказ без цитат. `--json` выводит один объект с вопросом, статусом, ответом, режимом поиска и цитатами; ошибки идут в stderr. Параметр `--retrieval-mode dense|reranked` действует только на этот вызов, по умолчанию используется `reranked`.

В `.env` доступны `GENERATION_PROVIDER=ollama`, `OLLAMA_BASE_URL=http://127.0.0.1:11434`, `OLLAMA_MODEL=qwen3.5:9b`, `OLLAMA_TIMEOUT_SECONDS=180` (1–600), `GENERATION_TEMPERATURE=0.1` (0–2) и `GENERATION_MAX_TOKENS=512` (1–4096). Для каждого ответа отправляется один запрос `POST /api/chat` без потоковой передачи и режима размышления. Проверка структуры ответа и цитат не доказывает фактическую точность: качество генерации требует отдельной оценки. Решение описано в `docs/decisions/0002-local-grounded-generation.md`.

### Оценка качества генерации

Отслеживаемый `data/evaluation/generation_questions.json` содержит 42 поддерживаемых вопроса из замороженного датасета поиска и 18 вопросов без ответа в активном корпусе. При наличии локальной Ollama и модели `qwen3.5:9b` запустите из `backend/`:

```powershell
python -m app.evaluation.generation_cli validate-dataset
python -m app.evaluation.generation_cli run
```

Полный запуск делает один запрос на каждый из 60 вопросов с текущими настройками Task009. Автоматические показатели охватывают правильность статуса ответа или отказа, успешность структурированного вывода, совпадение цитируемых источников и страниц с метками Task006, а также время ответа. Они **не измеряют достоверность текста**. Для неё отдельный файл `data/processed/evaluation/generation_manual_review.json` содержит ответ, цитаты, исходный текст цитируемых чанков и четыре оценки 0–2: фактическая точность, опора на контекст, полнота и поддержка цитатами. Оценки выставляет человек, языковая модель как судья не используется.

Итоги автоматического прогона сохраняются в `data/processed/evaluation/generation_report.json` и `.md`; все три файла игнорируются Git. После заполнения всех оценок выполните `python -m app.evaluation.generation_cli validate-review` и `python -m app.evaluation.generation_cli summarize-review`. Для явно неполного обзора используйте `summarize-review --partial`: он считает только полностью оценённые строки и показывает их число. Команды принимают `--dataset`, `--retrieval-dataset`, `--output-dir`; команды обзора также принимают `--review`. При отсутствии Ollama доступна проверка датасета, но реальные метрики генерации не создаются. До итогового представления результатов желательно вручную оценить все полученные поддерживаемые ответы. Метод описан в `docs/decisions/0003-generation-evaluation-method.md`.

Первый реальный прогон 60 вопросов на `qwen3.5:9b` завершён; автоматические результаты записаны в `docs/evaluation/0001-generation-baseline.md`. Ручная оценка фактической точности и опоры ответов на источники ещё не проведена.

## Frontend

В отдельном окне PowerShell из корня репозитория установите зависимости и запустите frontend:

```powershell
Set-Location frontend
npm ci
npm run dev
```

Откройте `http://localhost:5173` (этот origin должен совпадать с `FRONTEND_ORIGIN`). На демонстрационной странице помощник представлен плавающим виджетом: кнопка в правом нижнем углу → панель → вопрос → ответ с официальными источниками. Это демонстрация будущего встраивания справочного модуля в существующий сайт, а не развёрнутый сайт университета.

При загрузке страницы выполняется проверка доступности backend. Для получения ответа нужны оба подготовленных индекса, локальные модели поиска и работающая Ollama с `qwen3.5:9b`, как описано выше. Успешная health-проверка сама по себе не подтверждает готовность моделей.

«Помощник абитуриента СПбГЭУ» отвечает по официальному корпусу бакалавриата и специалитета приёмной кампании 2026 года. Примеры только заполняют поле. Enter отправляет вопрос, Shift+Enter добавляет строку. Предел — 2000 Unicode-символов исходного ввода, включая пробелы. Первый ответ может занять больше времени из-за загрузки моделей; автоматических повторов нет.

Каждый вопрос независим: новая отправка заменяет предыдущий результат, история не накапливается. Закрытие кнопкой или Escape сохраняет черновик, результат и состояние подключения до перезагрузки страницы; начатый запрос продолжает выполняться. После закрытия фокус возвращается кнопке запуска. Ответ отображается обычным текстом; ссылки на официальные источники открываются в новой вкладке. Страницы одного PDF объединяются только для отображения. Отказ из-за нехватки сведений показывается без источников. При ошибке можно явно повторить прежний вопрос.

На телефоне панель раскрывается почти на весь экран; открытие фокусирует заголовок, а поле выбирается касанием. На компьютере при готовом сервисе фокус сразу получает поле. Ответ прокручивается отдельно, форма остаётся внизу панели. Непосредственно под формой во всех открытых состояниях отображается уведомление:

> Ответ сформирован ИИ на основе официальных материалов СПбГЭУ. Важную информацию рекомендуем уточнять в приёмной комиссии.

Вложения, история и авторизация отложены. Следующий приоритет — жизненный цикл документов, версионирование и актуальность корпуса.

## Структура

- `backend/` — FastAPI приложение, конфигурация и focused-тесты.
- `frontend/` — React-приложение на TypeScript и Vite.
- `data/source_manifest.json` — утверждённые источники; `data/evaluation/` — проверочный набор вопросов; `data/processed/html/` и `data/processed/pdf/` — нормализованные документы; `data/processed/chunks/` — локальные чанки; `data/processed/index/` — локальный индекс.
- `docs/` — архитектурные принципы и целевой концептуальный поток.

Во время разработки приложения запускаются локально. Конфигурация адресов отделена от исходного кода, поэтому проект не привязан к компьютеру разработчика и допускает последующее серверное развёртывание. Конкретная production-инфраструктура здесь не задаётся.

### End-to-end API smoke

Для явной сквозной проверки подготовьте основной и табличный индексы (`build-index`, `build-table-index`), локальный кеш BGE-M3 и reranker, запустите Ollama с моделью `qwen3.5:9b`. Из `backend/`:

```powershell
python -m app.evaluation.api_smoke_cli run
```

Команда выполняет шесть фиксированных вопросов через FastAPI с реальным поиском и локальной Ollama в одном жизненном цикле приложения. Она не входит в обычный pytest, не скачивает модели или документы и не перестраивает индексы. Отсутствующие или устаревшие артефакты останавливают проверку. Все шесть случаев должны пройти; задержки имеют диагностический характер.

Отчёты `api_e2e_smoke.json` и `.md` записываются в игнорируемый `data/processed/evaluation/task023b/smoke/` (переопределение: `--output-dir`). Проверяются HTTP-контракт, статусы и цитаты источников/страниц. Успех подтверждает интеграцию, но не универсальную фактическую точность ответов; человеческая оценка Task020 остаётся отдельным свидетельством.


Контракт разрешённых свидетельств smoke находится в `data/evaluation/api_smoke_cases.json`: он допускает только проверенные источники и страницы, не меняя исторические метки Task006. Существующий отчёт smoke не перезаписывается.

После успешного smoke полный текущий baseline генерации можно измерить существующей командой (из `backend/`, в новый отдельный каталог):

```powershell
$env:HF_HUB_OFFLINE = "1"
$env:TRANSFORMERS_OFFLINE = "1"
python -c "from app.evaluation.api_smoke import preflight; preflight()"
# Продолжать только при успешной предварительной проверке.
python -m app.evaluation.generation_cli run --output-dir ../data/processed/evaluation/task023b/generation
python -m app.evaluation.api_smoke_cli validate-generation --report ../data/processed/evaluation/task023b/generation/generation_report.json
```

Проверка полного отчёта работает офлайн и требует 60 структурированных ответов без ошибок, в том числе точного отказа для всех 18 неподдерживаемых вопросов. Отказы на поддерживаемые вопросы перечисляются отдельно. Отчёты и пустая форма ручного обзора остаются локальными; автоматических семантических оценок нет. Исходные отчёты Task011 и Task023 сохраняются отдельно.


Текущая версия промпта — `grounded-answer-v2`: фактические вопросы решаются по официальному контексту; индивидуальные прогнозы поступления, персональный выбор программы, личные/оперативные статусы и неустановленные будущие факты требуют отказа. Модель и публичный ответ не меняются. Исторические отчёты Task011/018/020 относятся к v1; их результаты не переносятся автоматически на v2. Проверка `validate-generation` дополнительно сравнивает v2 с сохранённым полным прогоном Task023A и требует его неизменный SHA-256.

После прохождения полного v2-прогона и шестислучайного smoke отдельно проверяются два персональных вопроса через реальный API:

```powershell
python -m app.evaluation.api_smoke_cli safety-probes
```

Отдельные отчёты находятся в `data/processed/evaluation/task023b/safety/`. Они не входят в счётчик шести smoke-случаев. Решение и ограничения: [ADR 0006](docs/decisions/0006-explicit-answerability-policy.md).
